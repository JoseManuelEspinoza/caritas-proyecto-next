REPORTE DE SEGURIDAD
Sistema GRD — Cáritas Lima
Rama: dev_Jean_Pierre_Benites
Fecha: 15 de junio de 2026
1. Resumen Ejecutivo
Se realizó una revisión de seguridad sobre el código del sistema web GRD Cáritas Lima. El análisis cubrió los endpoints de sincronización móvil, las server actions de Next.js, la gestión de roles y permisos, y la capa de integración con AWS S3.
Se identificaron 6 hallazgos de seguridad en total: 1 crítico, 4 altos y 1 medio. Los dos hallazgos de mayor impacto (crítico y alto, confianza ≥ 9/10) son accionables de inmediato. Los 4 hallazgos adicionales (confianza 7–8/10) se presentan también para trazabilidad y mejora continua.
No se detectaron vulnerabilidades de SQL Injection (el proyecto usa Prisma ORM con queries parametrizadas) ni XSS (React escapa el HTML automáticamente).

2. Metodologia
La revision se realizo en tres fases:
Fase 1 — Contexto: identificacion de frameworks de seguridad existentes, patrones de autenticacion y modelo de roles.
Fase 2 — Analisis comparativo: comparacion del codigo nuevo contra patrones seguros establecidos en el proyecto.
Fase 3 — Evaluacion de vulnerabilidades: trazado de flujos de datos desde entradas del usuario hasta operaciones sensibles.
Se excluyo por diseno: DoS/agotamiento de recursos, secretos en disco, rate limiting, vulnerabilidades en librerias de terceros.
Herramientas: revision manual de codigo, analisis de flujo de datos, subagentes especializados de filtracion de falsos positivos.
3. Hallazgos Detallados
H1 [CRITICA] — Bypass de autenticacion en endpoints moviles
Archivo(s)
app/api/mobile/sync/*.ts, app/api/mobile/kits/route.ts
Severidad
CRITICA
Confianza
9/10
Categoria
Authentication Bypass
Descripcion
La funcion requireMobileSyncKey(), presente en todos los endpoints moviles, contiene un bypass explicito de desarrollo: si la variable de entorno MOBILE_SYNC_API_KEY no esta definida, devuelve null y el endpoint queda completamente abierto sin ningun mecanismo de autenticacion.
Codigo vulnerable:
const expected = process.env.MOBILE_SYNC_API_KEY;
if (!expected) return null; // sin env var = sin auth
El propio comentario en el codigo confirma el riesgo: "Para desarrollo permite probar sin key si no esta configurada. Para produccion, definir MOBILE_SYNC_API_KEY en .env del servidor." Sin embargo, no existe ningun mecanismo que impida que esto ocurra en produccion.
Escenario de explotacion
Si MOBILE_SYNC_API_KEY no esta presente en el entorno del servidor (nuevo despliegue, contenedor reiniciado, entorno de staging), un atacante puede:
Llamar a POST /api/mobile/sync/evidencias sin credenciales y crear registros falsos en la BD.
Usar POST /api/mobile/sync/entregas para registrar entregas de kits ficticias.
Usar POST /api/mobile/sync/incidencias para crear incidencias fraudulentas.
Generar presigned URLs de S3 a costo del servidor.
Correccion recomendada
Reemplazar el bypass silencioso por un rechazo explicito:
if (!expected) {
return NextResponse.json(
{ ok: false, message: 'Sincronizacion movil no configurada.' },
{ status: 503 }
);
}
Aplicar en todos los archivos bajo app/api/mobile/. Adicionalmente, agregar una asercion de arranque que detenga la aplicacion si la key no esta definida en entornos no-development.
H2 [ALTA] — Sin verificacion de rol en server actions
Archivo(s)
app/actions/incidents.ts, app/actions/kits.ts, app/actions/donaciones.ts
Severidad
ALTA
Confianza
9/10
Categoria
Escalacion de privilegios / Authorization Bypass
Descripcion
Las server actions de Next.js son el limite real de la API del servidor — son invocables via POST HTTP desde cualquier cliente con una cookie de sesion valida. Todas las acciones sensibles llaman a verifySession() para confirmar autenticacion, pero ninguna verifica el rol del usuario antes de ejecutar operaciones privilegiadas.
Accion
Rol requerido (diseno)
Control real
aprobarCaso / rechazarCaso
COMITEDONACIONES
Solo verifySession()
crearKit
ESPECIALISTAGRD
Solo verifySession()
registrarMovimientoKit
ESPECIALISTAGRD
Solo verifySession()
guardarArticulosKit
ESPECIALISTAGRD
Solo verifySession()
assignEquipo / assignBrigadista
ESPECIALISTAGRD
Solo verifySession()
Escenario de explotacion
Un brigadista de campo (rol mas bajo) invoca aprobarCaso() directamente via HTTP con su cookie de sesion. El servidor lo autentica exitosamente y ejecuta repo.resolverSolicitud(id, 'APROBADA'), aprobando casos humanitarios sin revision del comite y bypasseando el flujo de governance completo. Tambien puede depletar stock de kits con cantidades arbitrarias.
Correccion recomendada
// incidents.ts — aprobarCaso, observarCaso, rechazarCaso
const session = await verifySession();
if (!['COMITEDONACIONES','ADMINISTRADOR'].includes(session.role)) {
return { message: 'No tienes permisos para esta accion.' };
}
// kits.ts — crearKit, registrarMovimientoKit, guardarArticulosKit
const session = await verifySession();
if (!['ESPECIALISTAGRD','ADMINISTRADOR'].includes(session.role)) {
return { message: 'No tienes permisos para esta accion.' };
}
H3 [ALTA] — Identity spoofing via request body en sync movil
Archivo(s)
app/api/mobile/sync/evidencias/route.ts:129-163, app/api/mobile/sync/entregas/route.ts:272-290
Severidad
ALTA
Confianza
8/10
Categoria
Escalacion de privilegios
Descripcion
Los endpoints de sync movil leen la identidad del usuario actuante directamente desde el body JSON del request (idUsuarioCargaGRD, idUsuarioRemoto, idUsuarioGRD). Cualquier llamante puede suplantar a cualquier usuarioGRD simplemente incluyendo su ID en el payload.
Escenario de explotacion
Un atacante que logre llamar al endpoint (especialmente si H1 no esta corregido) incluye el UUID de un supervisor o administrador en el campo idUsuarioCargaGRD. Los registros quedan atribuidos a ese usuario en el sistema de auditoria, contaminando la trazabilidad y potencialmente disparando flujos o notificaciones asociadas a ese rol.
Correccion recomendada
Nunca derivar la identidad del usuario desde el request body. El endpoint movil debe autenticar al dispositivo/usuario mediante un token por-dispositivo, y usar exclusivamente esa identidad del lado del servidor para atribuir registros.
H4 [ALTA] — S3 key sin validar desde payload movil
Archivo(s)
app/api/mobile/sync/evidencias/route.ts:214-221
Severidad
ALTA
Confianza
8/10
Categoria
Validacion de entrada / Integridad de datos
Descripcion
Cuando no se provee base64, el endpoint acepta urlArchivo, urlS3 o key directamente desde el request body y los almacena en la BD como urlArchivo sin validar que correspondan a prefijos S3 conocidos. El endpoint web (app/api/archivos/route.ts) si valida prefijos conocidos, pero el path movil omite esta comprobacion.
Escenario de explotacion
Un atacante envia { "urlArchivo": "https://sitio-malicioso.com/phishing" }. El valor queda guardado en evidenciaGRD. Si algun componente de la UI renderiza ese valor como href o src sin validacion adicional, se convierte en un vector de phishing almacenado. Ademas, valores arbitrarios contaminan los registros de auditoria.
Correccion recomendada
Aplicar la misma lista blanca de prefijos usada en el upload web. Rechazar cualquier valor que no comience con un prefijo conocido (evidencia-kit/, evidencia-grd/, etc.) o que sea una URL externa completa.
H5 [ALTA] — Atribucion fantasma al usuario GRD mas antiguo
Archivo(s)
app/api/mobile/sync/evidencias/route.ts:152-163
Severidad
ALTA
Confianza
8/10
Categoria
Integridad de datos / No-repudio
Descripcion
Cuando ningun ID de usuario puede ser resuelto desde el payload o el entorno, el sistema silenciosamente atribuye el registro al usuario GRD activo mas antiguo de la BD (orderBy: fechaCreacion asc). Esto tipicamente corresponde al administrador o al primer especialista registrado.
Escenario de explotacion
Un request anonimo (potenciado por H1) que omite idUsuarioCargaGRD hace que el sistema registre la evidencia o entrega como si hubiera sido subida por el administrador del sistema. En un contexto humanitario con implicaciones legales, esto genera registros de auditoria falsos atribuidos a usuarios reales sin su conocimiento o consentimiento.
Correccion recomendada
Eliminar el fallback completamente. Si no es posible identificar al usuario, retornar un error 401/400. Nunca atribuir silenciosamente acciones a usuarios reales del sistema.
H6 [MEDIA] — GET endpoints moviles sin autenticacion
Archivo(s)
app/api/mobile/sync/evidencias/route.ts:223-230, app/api/mobile/sync/entregas/route.ts:456-463
Severidad
MEDIA
Confianza
7/10
Categoria
Exposicion de informacion / Reconocimiento
Descripcion
Los handlers GET de los endpoints de sync actuan como health-checks y no aplican requireMobileSyncKey. Actualmente retornan metadata benigna (nombre del endpoint, version), pero confirman a cualquier visitante anonimo la existencia y rutas exactas de las APIs internas de sincronizacion.
Escenario de explotacion
Un atacante hace GET /api/mobile/sync/evidencias sin credenciales y recibe confirmacion de que el endpoint existe y esta activo. Esto facilita el reconocimiento y dirige ataques posteriores a las rutas correctas. Ademas, si en el futuro un desarrollador agrega logica de lectura a estos handlers sin agregar auth, la brecha sera inmediata.
Correccion recomendada
Agregar requireMobileSyncKey a todos los handlers GET en rutas de sync movil, de la misma forma que se aplica en los handlers POST.
4. Vulnerabilidades Auditadas y No Encontradas
Tipo
Razon de exclusion
SQL Injection
El proyecto usa Prisma ORM con queries parametrizadas. No se detectaron queries raw con interpolacion de usuario.
XSS (Cross-Site Scripting)
React/Next.js escapa el HTML automaticamente. No se encontro uso de dangerouslySetInnerHTML con datos de usuario.
CSRF
Next.js Server Actions tienen proteccion CSRF built-in mediante el mecanismo de origin checking.
Path Traversal en S3
El endpoint web app/api/archivos/route.ts valida prefijos conocidos y rechaza rutas con '..'.
Command Injection
No se detectaron llamadas a shell o ejecucion de comandos del sistema con input de usuario.
JWT vulnerabilities
La autenticacion delega completamente en Keycloak y Auth.js v5, que manejan la validacion de tokens.
